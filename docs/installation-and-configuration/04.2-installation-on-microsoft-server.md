# Imperva Agent 14.9 Deployment — MS SQL Server

### Agent Installation, Quick Configuration, and IPC Interface Configuration

**Target:** Windows Server 2012 R2 (MS SQL Server 2014)
**Imperva Gateway Version:** 14.19.1.80_0
**Agent Version:** 14.9

---

## Overview

This procedure documents the full deployment of Imperva Agent v14.9 on an MS SQL Server 2014 host: database-side prerequisite login and native SQL Server auditing, the two-part Windows agent install (Agent + Agent Installation Manager), the interactive quick-configuration wizard, logical mapping and advanced plugin configuration in the MX Console, binding of the `MssQL IPC` interface to capture local SSMS traffic that runs over Shared Memory rather than TCP, security policy configuration, and production hardening/maintenance.

> Gateway and MX virtual-appliance deployment (OVF import, licensing, first-time-login network configuration) is covered separately in [04.3 — MX Server and Gateway Configuration](04.3-mx-server-and-gateway-configuration.md). This document assumes the MX and Gateway are already up, licensed, and reachable, and that a listener for remote agents has already been configured on the Gateway (`impcfg` → option 2 → option 5 → Remote Agents screen).

## 1. Prerequisites and Planning

**Pre-deployment checklist**
1. Windows Server 2012 R2 (or later) with latest updates
2. SQL Server 2014 SP3 or higher installed
3. Administrator credentials for the Windows server
4. SQL Server sysadmin credentials
5. Network connectivity verified between the SQL Server, Gateway, and MX
6. Firewall rules documented and approved
7. Imperva license file obtained and applied to the MX
8. MX Management Server accessible
9. DAM Gateway deployed, licensed, and its remote-agent listener configured
10. Windows Agent installer(s) downloaded from the MX or Imperva FTP
11. Service accounts created (domain account recommended for production)
12. Backup and maintenance windows scheduled

**Windows Server preparation**
1. Login to the Windows Server as Administrator
2. Verify the OS is fully patched
3. Check available disk space (minimum 10 GB free on `C:`)
4. Verify .NET Framework 4.5+ is installed
5. Ensure SQL Server is running and accessible
6. Document SQL Server instance name(s) and port(s)
7. Temporarily disable UAC for the installation if prompted (re-enable afterward per your hardening policy)

**Windows Firewall configuration**
```powershell
# Run as Administrator

# Allow outbound HTTPS from the agent to the DAM Gateway(s)
New-NetFirewallRule -DisplayName "Imperva Agent to Gateway" `
  -Direction Outbound -Protocol TCP `
  -RemoteAddress 192.168.10.243 `
  -RemotePort 443 -Action Allow

# Verify rule creation
Get-NetFirewallRule -DisplayName "Imperva Agent to Gateway"

# Alternative: Control Panel -> Windows Firewall -> Advanced Settings
# -> Outbound Rules -> New Rule -> Port -> TCP 443
```

> **Note:** Windows requires the installer to be run **as Administrator**; every other OS (Linux/Unix) requires **root**-level access for the equivalent agent install.

## 2. Database Prerequisites — Agent User Creation

**Run on the target MS SQL instance, in the `master` database:**

```sql
-- Switch to the master database to create the server-level login
USE master;
GO

-- Create the login for the Imperva agent
CREATE LOGIN imperva_monitor WITH PASSWORD = 'YourSecurePasswordHere',
  DEFAULT_DATABASE = [master],
  CHECK_EXPIRATION = OFF,
  CHECK_POLICY = OFF;
GO

-- Or, for Windows Authentication (recommended for production):
CREATE LOGIN [DOMAIN\imperva_monitor] FROM WINDOWS;
GO

-- Grant the required server-level permissions for passive monitoring
GRANT VIEW ANY DEFINITION TO imperva_monitor;
GRANT VIEW SERVER STATE TO imperva_monitor;
GO

-- Create a database user in each monitored database and grant minimal read-only visibility
USE [YourDatabaseName];
GO
CREATE USER [imperva_monitor] FOR LOGIN [imperva_monitor];
GO
GRANT VIEW DEFINITION TO [imperva_monitor];
GRANT VIEW DATABASE STATE TO [imperva_monitor];
GO
```

> **Note:** These are server-level, read-only visibility permissions. They allow the agent to resolve object and session metadata for audit purposes — they do **not** grant access to user data.

**Verify granted permissions**
```sql
SELECT
  pr.name AS [Principal],
  pr.type_desc AS [Type],
  pe.permission_name,
  pe.state_desc
FROM sys.server_permissions pe
INNER JOIN sys.server_principals pr ON pe.grantee_principal_id = pr.principal_id
WHERE pr.name = 'imperva_monitor'
ORDER BY pe.permission_name;
GO
```

### 2.1 Enable native SQL Server Audit (defense in depth)

SQL Server 2014's built-in audit functionality complements agent-based monitoring and gives an independent, database-native record.

```sql
-- Create Server Audit
USE [master];
GO
CREATE SERVER AUDIT [Imperva_Server_Audit]
TO FILE
( FILEPATH = N'C:\SQLAudit\',
  MAXSIZE = 100 MB,
  MAX_ROLLOVER_FILES = 20,
  RESERVE_DISK_SPACE = OFF )
WITH ( QUEUE_DELAY = 1000, ON_FAILURE = CONTINUE );
GO

ALTER SERVER AUDIT [Imperva_Server_Audit] WITH (STATE = ON);
GO

-- Server Audit Specification
CREATE SERVER AUDIT SPECIFICATION [Imperva_Server_Audit_Spec]
FOR SERVER AUDIT [Imperva_Server_Audit]
  ADD (FAILED_LOGIN_GROUP),
  ADD (SUCCESSFUL_LOGIN_GROUP),
  ADD (LOGOUT_GROUP),
  ADD (SCHEMA_OBJECT_CHANGE_GROUP),
  ADD (DATABASE_OBJECT_CHANGE_GROUP),
  ADD (SERVER_PERMISSION_CHANGE_GROUP),
  ADD (DATABASE_PERMISSION_CHANGE_GROUP)
WITH (STATE = ON);
GO

-- Database Audit Specification (repeat per monitored database)
USE [YourDatabaseName];
GO
CREATE DATABASE AUDIT SPECIFICATION [Imperva_DB_Audit_Spec]
FOR SERVER AUDIT [Imperva_Server_Audit]
  ADD (SELECT, INSERT, UPDATE, DELETE ON SCHEMA::[dbo] BY [public]),
  ADD (EXECUTE ON SCHEMA::[dbo] BY [public]),
  ADD (SELECT ON OBJECT::[dbo].[SensitiveTable] BY [public]),
  ADD (UPDATE ON OBJECT::[dbo].[SensitiveTable] BY [public])
WITH (STATE = ON);
GO
```

### 2.2 Configure Extended Events (optional, low-overhead detail capture)

```sql
CREATE EVENT SESSION [Imperva_XE_Session] ON SERVER
ADD EVENT sqlserver.sql_statement_completed
(
  ACTION (sqlserver.client_app_name, sqlserver.client_hostname, sqlserver.database_name,
          sqlserver.server_principal_name, sqlserver.session_id, sqlserver.sql_text)
  WHERE ([sqlserver].[database_name] <> N'tempdb')
),
ADD EVENT sqlserver.rpc_completed
(
  ACTION (sqlserver.client_app_name, sqlserver.client_hostname, sqlserver.database_name,
          sqlserver.server_principal_name, sqlserver.session_id)
),
ADD EVENT sqlserver.login
(
  ACTION (sqlserver.client_app_name, sqlserver.client_hostname, sqlserver.server_principal_name)
)
ADD TARGET package0.event_file
(
  SET filename = N'C:\SQLAudit\XE\Imperva_XE.xel',
      max_file_size = (50), max_rollover_files = (10)
)
WITH (MAX_MEMORY = 4096 KB, MAX_DISPATCH_LATENCY = 30 SECONDS);
GO

ALTER EVENT SESSION [Imperva_XE_Session] ON SERVER STATE = START;
GO
```

**Ensure TCP/IP is enabled** on the SQL Server instance (SQL Server Configuration Manager → SQL Server Network Configuration → Protocols → TCP/IP → Enabled = Yes, port 1433 under the IPAll section), then restart the SQL Server service for the change to take effect.

## 3. Agent Installation (Interactive)

**Navigation:** Run installer as **Administrator** on the Windows VM.

Imperva ships **two** installers for Windows, and both should be installed:

- **Agent** — the actual monitoring agent binary.
- **Agent Installation Manager** ("the installer") — despite the name, this does **not** install the agent; it keeps the already-installed agent up to date and compatible with the latest Windows patches. It is not strictly required for the agent to function, but is highly recommended.

Retrieve the binaries from the Imperva FTP site (`ftp.imperva.com`, via browser or FileZilla): **Downloads → Imperva Agents → \<version> → Windows** → download the latest release for your agent version (e.g. `14.9`), plus its `.md5` checksum file to validate the download.

### 3.1 Install the Agent

1. Right-click the Agent MSI → **Run as administrator** (required on Windows; other OSes require root).
2. Accept the installer defaults and let it load.
3. From the on-screen menu, choose **option 1 — Quick Configuration**.
4. Work through the quick-configuration prompts:

   | Prompt | Response |
   | --- | --- |
   | Should database traffic be monitored? | `Yes` / `True` |
   | Agent (remote agent) name | Name it after the database server, e.g. `mssql_agent_01` |
   | Gateway management listener IP address | The Gateway's IP, e.g. `192.168.10.243` |
   | Monitor traffic: Local, Network, or Both? | `Both` (local **and** network) |
   | Gateway login password | The password assigned to the built-in **Imperva** account during Gateway setup |

5. On success you will see **"the remote agent was successfully registered"** — press any key to continue.
6. When asked **"Start the agent?"**, answer **Yes**.
7. Close the installer once it reports the agent is installed.

### 3.2 Install the Agent Installation Manager

1. Launch the second installer ("Agent Installer" / Agent Installation Manager) → **Next**.
2. It detects the existing agent and offers to copy the previous configuration — choose **Yes, use configuration**.
3. **"Use the installed Imperva agent registration information?"** → **Yes**.
4. **Location of the agent installation manager packages** → accept the default folder.
5. **Cache size** → double the default (this cache is local staging space the installer uses to push updates/patches to the agent — a little extra headroom is recommended).
6. Let it register and complete — it will report **"Registering... installer is now complete."**
7. Confirm **Yes** to start the **Agent Installation Manager** service, then close the installer.

### 3.3 Silent Installation (Command Line)

For scripted/unattended rollouts, the agent MSI supports silent install switches:

```cmd
REM Run from an elevated command prompt

```

## 4. Logical Mapping in MX Console

**Navigation:** `Main > Setup > Sites / Agents`

1. Confirm the site tree — at minimum the correct **Server Group** and **Service** object must already exist before the agent is registered, so it can be assigned to the right service.
2. Add the Windows VM as a **Server** under the target Server Group (e.g. `windows_server_db`)
3. Go to **Agents**, select the agent that was just installed (e.g. `mssql_agent_01`) — if several agents are listed, make sure the correct one is selected
4. Go to the agent's **Settings** tab → **Default Server Group**, select the target Server Group, and **Save first** — the associated Service object only appears in the list *after* the Server Group has been saved
5. Select the Service object that appears (e.g. `ms_sql_2014`) and click **Assign**, then **Assign now**
6. Under the service's traffic-source mapping, set **Source IP** and **Destination IP** to the *same* address (the database server's own IP) for connections made locally on the box — otherwise local activity shows up as source `0.0.0.0`, which is easy to misread. For connections from other machines, the source IP will correctly show the originating host and the destination IP will show the SQL Server itself.
7. Set the **Destination Port** to `1433` (the SQL Server default, unless a custom port is used)
8. Click **Save** — if you navigate away with unsaved changes, the console will warn you; if a change doesn't appear to take effect, it's almost always because **Save** was skipped

**Verify agent + Agent Installation Manager in MX**

Navigate to **Agents** — the newly installed agent should be listed, and its entry should also show the **Installation Manager** as present, confirming both installers succeeded. If the Installation Manager is not shown here, something went wrong with that second install and it should be re-run.

### 4.1 Advanced Configuration — Plugin Keys

**Navigation:** Agent → **Settings** → **Advanced Configuration**

Two plugin keys are commonly set for MS SQL agents:

| Key | Value | Purpose |
| --- | --- | --- |
| `mssql-advanced-monitoring` | `1` (true) / `0` (false) | Lets the agent inspect encrypted/"hashed" transactions more deeply. Without it, sessions using encrypted logins show up as a **hashed user** instead of the real username; enabling it resolves the actual username in the audit log. |
| *(IPv6 listener key)* | `0` (false) / `1` (true) | Disables the IPv6 listener when IPv6 is not in use on the server. Without disabling it, the agent repeatedly reports "IPv6 present, not monitored" notifications that are just noise if IPv6 truly isn't being used. |

After entering both keys, click **Save**. Configuration changes are **pull-based**: the agent periodically checks in with the Gateway for new instructions rather than the Gateway pushing to the agent directly. To apply the change immediately rather than waiting for the next poll interval, right-click the agent → **Restart Agent**, supply a reason (e.g. "advanced monitoring enabled"), and confirm. On its next check-in the agent receives the restart command, reconnects to the Gateway, pulls the new configuration (advanced monitoring on, IPv6 events off), and complies — no need to touch the database server itself again once the agent and installer are in place.

**Confirm the agent is live:** refresh the agent list — **Last Activity** should update once any database traffic occurs, and **Throughput** will remain `0` until real traffic is sent, at which point it reflects ongoing activity. This confirms the agent is communicating, up, and healthy.

## 6. Capturing Local SSMS Traffic — IPC Interface

Local queries run through SQL Server Management Studio (SSMS) on the database server use **Shared Memory**, not TCP, so they bypass the agent's standard network sniffer. Capturing this traffic requires a dedicated IPC interface.

**Navigation:** `Main > Setup > Agents > mssql_agent_01 > Data Interfaces tab`

1. Add a new **Data Interface** of type `MssQL IPC`
2. Bind the IPC interface to the `ms_sql_2014` service
3. Set the **Server Path** to the named pipe:

```
\\.\pipe\sql\query
```

> **Why this matters:** This is the MS SQL equivalent of Oracle BEQ/IPC binding. Network-based sniffers only see remote connections — a DBA or application using SSMS directly on the database server communicates over Shared Memory, which stays invisible to the agent until the `MssQL IPC` interface is explicitly bound to the service.

## 7. Network Monitoring Configuration (Optional — passive SPAN/TAP redundancy)

In addition to agent-based monitoring, Imperva DAM can passively monitor SQL Server traffic using network SPAN/TAP. This provides redundancy and can capture traffic from sources that cannot have an agent installed.

| Component | Purpose | Configuration |
| --- | --- | --- |
| Network Switch | Traffic mirroring source | SPAN port configured |
| DAM Gateway NIC | Traffic capture interface | Promiscuous mode |
| SQL Server Traffic | Target traffic to monitor | Port 1433 |
| Gateway Analysis | Packet inspection and logging | Deep packet inspection |

**Cisco switch SPAN example**
```
configure terminal
monitor session 1 source interface GigabitEthernet1/0/1
monitor session 1 destination interface GigabitEthernet1/0/24
show monitor session 1

! Alternative: RSPAN for remote monitoring
monitor session 1 source interface Gi1/0/1
monitor session 1 destination remote vlan 100
```

**Gateway-side configuration**
```
configure
interface eth1
mode promiscuous
enable

network-monitoring enable
network-monitoring interface eth1
network-monitoring port 1433

exit
save configuration
show network-monitoring status
```

**Add the network-based database service**
1. **Data Sources → Database Services → Add Database Service**
2. Service Name: `PROD_MSSQL_NETWORK_MONITOR`; Connection Method: **Network Monitoring (SPAN/TAP)**
3. Gateway: select the gateway with network monitoring enabled; Server IP: the SQL Server host; Port: `1433`; Protocol: **TDS**
4. Click **Test** to verify traffic capture, then **Save**

## 8. Security Policy Configuration

Create a base policy (`MSSQL_2014_Production_Security_Policy`) applied to the service/group above, assigned to all relevant gateways, priority **High (100)**, status **Enabled**. Configure the following rules under it:

| # | Rule | Key configuration | Actions | Severity |
| --- | --- | --- | --- | --- |
| 1 | Monitor Privileged Access (sa/sysadmin) | Users: `sa`, `BUILTIN\Administrators`, `sysadmin` role members; all operations; excludes health-check queries | Audit + Alert (email DBA + security teams, SIEM forward) | High |
| 2 | SQL Injection Detection | Signature + anomaly detection: `UNION SELECT`, `OR 1=1`, `EXEC xp_cmdshell`, `WAITFOR DELAY`, tautologies, comment injection (`--`, `/* */`), stacked queries | Audit + Alert + Block (terminate session) | Critical |
| 3 | Sensitive Data Access (PII/PCI/PHI) | Tables: `Customers`, `CreditCards`, `Employees`, `PatientRecords`; columns: SSN, CreditCardNumber, DOB, Email, Phone, Salary; tags PII/PCI-DSS/PHI(HIPAA)/GDPR; bulk threshold > 1000 rows; excludes approved reporting/ETL accounts | Audit + Alert (daily compliance summary) | Medium (High for bulk access) |
| 4 | After-Hours Access Monitoring | Mon–Fri 18:00–06:00, Sat–Sun all day, integrated with the corporate holiday calendar; excludes batch/automated/backup accounts; alerts on unexpected source IPs | Audit + Alert (page on-call DBA after 2 violations) | High |
| 5 | Failed Authentication Monitoring | 5 failures in 10 minutes per user/source IP; ML-based brute-force and password-spray detection | Audit + Alert + Auto-block (1 hour, configurable); ServiceNow incident | High (Critical if > 20 attempts) |
| 6 | Detect Data Exfiltration | Rows > 10,000 or data volume > 100 MB; `SELECT INTO`, `BCP`, `OPENROWSET`, `xp_cmdshell`; full table scans without `WHERE`; sequential large queries; excludes authorized reporting/ETL users | Audit + Alert (Block for critical); CISO notification if > 100,000 rows | Critical |
| 7 | Database Configuration Changes | DDL (`CREATE`/`ALTER`/`DROP` DATABASE/TABLE/INDEX/VIEW), `GRANT`/`REVOKE`/`DENY`, `sp_configure` changes, login/role changes, backup/restore; scoped to DBA team and approved change windows | Audit + Alert + change validation against ServiceNow | High |
| 8 | Excessive Privilege Usage | `sysadmin`/`db_owner`/`db_securityadmin` roles used for routine SELECT/UPDATE instead of least-privilege accounts | Audit + Alert + weekly usage report | Medium |

**Performance impact testing**

Establish a baseline with SQL Server DMVs before enabling the agent, then compare CPU utilization, query response times, agent resource usage, network throughput, and disk I/O latency. Acceptable thresholds: agent CPU < 10%, agent memory < 2 GB, SQL query overhead < 5%, no timeouts or query failures.

```sql
-- CPU usage
SELECT SQLProcessUtilization AS SQL_CPU, SystemIdle,
       100 - SystemIdle - SQLProcessUtilization AS Other_CPU
FROM (
  SELECT TOP 1
    record.value('(./Record/@id)[1]', 'int') AS record_id,
    record.value('(./Record/SchedulerMonitorEvent/SystemHealth/SystemIdle)[1]', 'int') AS SystemIdle,
    record.value('(./Record/SchedulerMonitorEvent/SystemHealth/ProcessUtilization)[1]', 'int') AS SQLProcessUtilization
  FROM (
    SELECT timestamp, CONVERT(xml, record) AS record
    FROM sys.dm_os_ring_buffers
    WHERE ring_buffer_type = N'RING_BUFFER_SCHEDULER_MONITOR'
  ) AS x
  ORDER BY timestamp DESC
) AS y;

-- Top 10 queries by duration
SELECT TOP 10
  qs.total_elapsed_time / qs.execution_count AS avg_elapsed_time_ms,
  qs.execution_count,
  SUBSTRING(st.text, (qs.statement_start_offset/2)+1,
    ((CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(st.text)
      ELSE qs.statement_end_offset END - qs.statement_start_offset)/2) + 1) AS statement_text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY avg_elapsed_time_ms DESC;

-- Wait statistics
SELECT TOP 10 wait_type, wait_time_ms, signal_wait_time_ms, waiting_tasks_count
FROM sys.dm_os_wait_stats
WHERE wait_type NOT LIKE '%SLEEP%'
ORDER BY wait_time_ms DESC;
```

## 10. Production Rollout and Hardening

**Configure a domain service account for the agent**
```powershell
# Active Directory Users and Computers -> New User
# Username: svc-imperva-agent, password set to never expire
# Local Security Policy -> User Rights Assignment:
#   - Log on as a service
#   - Access this computer from the network

$serviceName = "Imperva Agent Service"
$domainAccount = "DOMAIN\svc-imperva-agent"
$password = "SecureP@ssw0rd"
$secPassword = ConvertTo-SecureString $password -AsPlainText -Force
$cred = New-Object System.Management.Automation.PSCredential($domainAccount, $secPassword)

Stop-Service $serviceName
$service = Get-WmiObject Win32_Service -Filter "Name='$serviceName'"
$service.Change($null,$null,$null,$null,$null,$null,$domainAccount,$password)
Start-Service $serviceName
```

**Automated health-monitoring script** (`Monitor-ImpervaAgent.ps1`, scheduled every 5 minutes):
```powershell
param(
  [string]$EmailTo = "dba-team@company.com",
  [string]$SMTPServer = "smtp.company.com"
)
$serviceName = "Imperva Agent Service"
$agentLog = "C:\Program Files\Imperva\Agent\logs\agent.log"

$service = Get-Service $serviceName -ErrorAction SilentlyContinue
if ($service.Status -ne 'Running') {
  Send-MailMessage -To $EmailTo -From "monitoring@company.com" `
    -Subject "CRITICAL: Imperva Agent Service Down on $env:COMPUTERNAME" `
    -Body "The Imperva Agent service is not running. Attempting restart..." -SmtpServer $SMTPServer
  Start-Service $serviceName
  Start-Sleep -Seconds 10
  $service = Get-Service $serviceName
  if ($service.Status -eq 'Running') {
    Send-MailMessage -To $EmailTo -From "monitoring@company.com" `
      -Subject "INFO: Agent Restarted" -Body "Imperva Agent service successfully restarted on $env:COMPUTERNAME" -SmtpServer $SMTPServer
  }
}

$errors = Select-String -Path $agentLog -Pattern "ERROR" | Select-Object -Last 10
if ($errors.Count -gt 5) {
  Send-MailMessage -To $EmailTo -From "monitoring@company.com" `
    -Subject "WARNING: High error count in Imperva Agent log" `
    -Body "Found $($errors.Count) errors in agent log on $env:COMPUTERNAME" -SmtpServer $SMTPServer
}
```
