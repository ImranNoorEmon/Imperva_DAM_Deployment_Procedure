## Agent Installation on Linux — Oracle / Oracle Linux Deployment

The deployment was performed on a **designated test database environment** rather than the live IPEMIS production servers. This approach allows policy tuning, baseline establishment, and verification before any production change. The procedure below is written for an **Oracle 19c** database running on **Oracle Linux 7.x/8.x** (agent-based architecture — no network SPAN/TAP required), and folds in the full lifecycle from prerequisites through production hardening.

> Gateway and MX virtual-appliance deployment (OVF import, licensing, and first-time-login network configuration) is covered separately in [04.3 — MX Server and Gateway Configuration](04.3-mx-server-and-gateway-configuration.md). This document assumes the MX and Gateway are already up and reachable.

---

### 1. Prerequisites and Planning

**Database server hardware/OS**
| Specification | Requirement |
| --- | --- |
| CPU | Verify sufficient headroom — the agent adds roughly 5–10% CPU overhead |
| Memory | Agent requires 512 MB – 2 GB RAM |
| OS | Oracle Linux 7.9+ or Oracle Linux 8.x |
| Kernel | 3.10+ (OL7) or 4.18+ (OL8) |
| Storage | 10–20 GB free (typically under `/opt`) for agent binaries and logs |

**Pre-deployment checklist**
1. Oracle Linux server patched and validated (`cat /etc/oracle-release`, `uname -r`)
2. Oracle 19c installed and the target PDB confirmed
3. Root (or sudo) credentials for the database host
4. Oracle DBA/SYSDBA credentials
5. Network connectivity confirmed between the database host, the Gateway, and the MX Server
6. Firewall rules documented and approved (see table below)
7. Imperva license file obtained and applied to the MX
8. Gateway virtual appliance deployed and registered with the MX (see [04.3](04.3-mx-server-and-gateway-configuration.md))
9. Linux agent package downloaded (RPM or `.bsx`/`install.sh` bundle, see Phase 0 below)
10. Backup and maintenance windows scheduled with the DB owner

**Firewall rules required**
| Source | Destination | Port | Protocol | Purpose |
| --- | --- | --- | --- | --- |
| Oracle Linux (agent) | DAM Gateway | 443 | TCP | Outbound agent → Gateway communication (SSL) |
| DAM Gateway | MX Server | 8083 | TCP | Management |
| DAM Gateway | NTP Server | 123 | UDP | Time sync |
| Admin workstation | MX Server | 8083 | TCP | Console access |

```bash
# Allow the agent to reach the DAM Gateway(s)
firewall-cmd --permanent --add-rich-rule='rule family="ipv4" \
  destination address="<gateway_primary_ip>" port port="443" \
  protocol="tcp" accept'

firewall-cmd --permanent --add-rich-rule='rule family="ipv4" \
  destination address="<gateway_secondary_ip>" port port="443" \
  protocol="tcp" accept'

firewall-cmd --reload
firewall-cmd --list-all
```

**SELinux — initial installation**

For the first installation, set SELinux to permissive so the agent kernel hooks are not blocked while a proper policy is generated. It is re-enabled with a custom policy during production hardening (Section 8).

```bash
getenforce
setenforce 0                       # temporary, until reboot
# Or, to persist across reboots (requires a reboot to take effect):
vi /etc/selinux/config
# SELINUX=permissive
```

**Required OS packages** (Oracle Linux 7.x example — adjust for OL8):

```bash
yum update -y   # test in non-prod first

yum install -y glibc glibc-devel libstdc++ openssl \
  openssl-libs kernel-headers kernel-devel gcc make \
  wget net-tools bind-utils

rpm -qa | grep -E "glibc|libstdc|openssl"
```

### 2. Phase 0 — Agent Installation on the Database Server

**Step 1: Identify the correct agent package**

Because there are many Linux/Unix kernel flavors, use the reconnaissance script rather than guessing the package name.

```bash
# Imperva FTP: Downloads → Securesphere Agents → Miscellaneous → which_ragent.sh (+ KABI file if required)
chmod +x which_ragent.sh
./which_ragent.sh -v <agent_version>          # e.g. -v 14.0000 for a 14.x agent
# Script analyses OS version, kernel version, and architecture,
# then reports the exact agent package name compatible with this system.
```

> **Note:** `which_ragent.sh` is updated far less often than the agent packages themselves — treat its output as a name to search for under `Downloads → Imperva Agents → <version> → <OS>` on the FTP site, not as a literal current filename. Some kernels also require a companion **KABI** file, downloaded from the same Miscellaneous folder.

**Step 2: Retrieve the agent package**

Two install paths are supported, depending on how the package is distributed for your OS/version:

- **RPM-based install** (most current Linux builds):
  ```bash
  # From an admin workstation
  scp imperva-ragent-<version>.x86_64.rpm root@<db_host>:/tmp/
  # or download directly on the server
  cd /tmp && wget http://<mx_ip>:8080/downloads/imperva-ragent-<version>.x86_64.rpm

  ls -lh imperva-ragent-*.rpm
  rpm -ivh imperva-ragent-<version>.x86_64.rpm

  ls -la /opt/imperva/ragent/
  /opt/imperva/ragent/bin/ragent --version
  systemctl status ragent
  ```
- **`.bsx` / `install.sh` bundle** (legacy / kernel-module installers, used on the DPE hosts in this deployment):
  ```bash
  chown root:root install.sh
  ```

**Step 3: Configure Secure Boot support (if applicable)**

> **Prerequisite:** `mokutil` must be installed. It is available through the `mokutil` package — refer to your database vendor's documentation for installation guidance.

If the target server has UEFI Secure Boot enabled, the Imperva kernel module key must be enrolled **before** the agent is installed, otherwise the kernel will block the driver.

1. Unzip the SecureSphere Agent installation package and run the following in the extraction directory:
   ```bash
   mokutil --import public_key_OEL-v7-kUEK-v3-px86_64.der
   ```
   > **Note:** The filename may differ depending on the agent version. This extracts the public key and prompts for a password.

2. Set a password and note it down — it will be required in the next step. Open a console to the database server and reboot it. Do not press any key until the server comes up and the automated UEFI key enrollment screen appears — you have only **10 seconds** to press any key to enter the UEFI key enrollment process. Follow the wizard's steps.

3. When prompted, enter the password created in step 2. Once complete, the key is registered and the server will reboot. Wait for the server to come back up — do **not** re-enter the BIOS or UEFI screen.

4. Verify the Imperva key appears in the keyring:
   ```bash
   mokutil --list-enrolled | grep Imperva
   ```
   Expected output:
   ```
   [root@localhost tmp]# mokutil --list-enrolled | grep Imperva
        Issuer: O=Imperva Inc., CN=Imperva Inc./emailAddress=support@imperva.com
        Subject: O=Imperva Inc., CN=Imperva Inc./emailAddress=support@imperva.com
   [root@localhost tmp]#
   ```

5. Once the output is verified:
   - If the agent is **not** installed, proceed to install it now (Step 4 below)
   - If a SecureSphere Agent that supports Secure Boot (**v13.2 or newer**) is already installed, simply restart the agent

**Step 4: Execute the installer**
```bash
# Run as root
./install.sh
# OR
./agent_package.bsx
# Provide the KABI file path when prompted (Linux/Oracle deployments)
# The installer hooks the agent into the OS kernel
```

**Step 5: Configure the agent (interactive)**

```bash
cd /opt/imperva/ragent/bin
./agentctl configure

# Interactive configuration prompts:
# 1. Primary gateway IP: <gateway_primary_ip>
# 2. Primary gateway port: 443
# 3. Add secondary gateway? y/n
# 4. Secondary gateway IP: <gateway_secondary_ip>
# 5. Agent display name: ORA-DB01-AGENT
# 6. Site name: <site_name>
# 7. Use SSL/TLS encryption? y
```

The same information can be set (or reviewed) directly in the agent's configuration file, `/opt/imperva/ragent/config/agent.conf`:

```ini
[agent]
agent_name = ORA-DB01-AGENT
site_name = Primary-Datacenter
primary_gateway = <gateway_primary_ip>:443
secondary_gateway = <gateway_secondary_ip>:443
use_ssl = true
monitor_network = true
monitor_audit_logs = true
max_memory_mb = 2048
log_level = INFO
```

### 3. Agent Registration & Connectivity — Summary

- **Ports:** The agent only requires an **outbound** connection to the Gateway on **TCP 443 (SSL)**. No inbound ports need to be opened on the database server for the agent itself.
- **Configuration files:** The agent's connection to the Gateway is defined in `cov_proxy.xml` (Gateway host, port, and SSL flag, plus the agent's registered name) — this is the legacy `.bsx`/`install.sh` equivalent of `agent.conf` above. If a registration attempt doesn't complete automatically, a `registration.xml` file can be used to mark the agent as registered so the service starts cleanly.
- **What the agent needs to do:** Register itself with the Gateway (either interactively, via the `ragentctrl register` CLI command or `agentctl configure`, or manually through the config files above), then run persistently as a `systemd` service so it survives reboots and restarts on failure.
- **Before reinstalling or re-registering:** Stop and clear any stale agent processes and remove leftover lock files to avoid registration conflicts.

### 4. Enable Persistence & Start the Agent Service

```bash
systemctl daemon-reload
systemctl enable ragent
systemctl start ragent
```

Final status check:
```bash
systemctl status ragent
```

Review the logs to confirm a successful registration and that Oracle monitoring came up for the correct SID:
```bash
tail -f /opt/imperva/ragent/logs/ragent.log
# Look for:
# [INFO] Agent started successfully
# [INFO] Connected to primary gateway <gateway_primary_ip>:443
# [INFO] Oracle database monitoring initialized for SID: orcl
```

**Verify agent registration in the MX Console**
1. Login to the MX Console (`https://<mx_ip>:8083`)
2. Navigate to **System → Agents**
3. Locate the agent (e.g. `ORA-DB01-AGENT`) in the list
4. Verify **Status:** Connected (green indicator)
5. Check **Gateway:** shows the correct Gateway name
6. Confirm **Last Heartbeat:** < 1 minute ago
7. Verify **Version** matches what was installed

### 5. Database User Configuration (Oracle)

Create the monitoring user inside the Oracle Database so the agent can see activity.

```bash
su - oracle
sqlplus / as sysdba
```

Ensure the database and PDB are open:
```sql
STARTUP;
ALTER PLUGGABLE DATABASE ORCLPDB OPEN;
ALTER PLUGGABLE DATABASE ORCLPDB SAVE STATE;
-- (If STARTUP says "already open," ignore it and run the next lines)
```

Switch to the PDB:
```sql
ALTER SESSION SET CONTAINER = ORCLPDB;
```

Run the user creation script:
```sql
CREATE USER imperva_monitor IDENTIFIED BY "StrongPassword123!";
GRANT CREATE SESSION TO imperva_monitor;
GRANT SELECT ON V_$SESSION TO imperva_monitor;
GRANT SELECT ON V_$SQL TO imperva_monitor;
GRANT SELECT ON V_$SQLTEXT TO imperva_monitor;
GRANT SELECT ON V_$SQLAREA TO imperva_monitor;
GRANT SELECT ON DBA_USERS TO imperva_monitor;
GRANT SELECT ON DBA_AUDIT_TRAIL TO imperva_monitor;

-- Verify user creation
SELECT username, account_status, created
FROM dba_users
WHERE username = 'IMPERVA_MONITOR';
```

**Enable Oracle Unified Auditing**

Oracle 19c's Unified Auditing gives the agent/gateway a second, database-native record to correlate against network- and agent-captured traffic.

```sql
-- Check unified audit status
SELECT * FROM V$OPTION WHERE PARAMETER = 'Unified Auditing';

-- Enable unified auditing (requires restart if not already active)
SHUTDOWN IMMEDIATE;
STARTUP;

-- Create and enable an audit policy scoped to sensitive tables and privileged actions
CREATE AUDIT POLICY imperva_audit_policy
  ACTIONS
    SELECT ON CUSTOMERS,
    INSERT ON CUSTOMERS,
    UPDATE ON CUSTOMERS,
    DELETE ON CUSTOMERS,
    ALTER SYSTEM,
    CREATE USER,
    DROP USER;

AUDIT POLICY imperva_audit_policy;
```

**Add the database service and run discovery in the MX Console**

1. Navigate to **Data Sources → Database Services → Add Database Service**
2. Service Name: `PROD_ORACLE_19C_DB01`; Database Type: `Oracle`; Version: `19c`
3. Connection Method: **Agent-Based Monitoring**; Agent: the one registered above
4. IP Address / Port: DB host IP, `1521`; SID / Service Name: `orcl` / `orcl.company.local`
5. Enter monitoring credentials (`imperva_monitor`), click **Test Connection**, then **Save**
6. Under **Schema Discovery**, select all schemas/tables/views/procedures, choose discovery depth **Full**, and click **Run Discovery**
7. Review discovered schemas, tables, and any sensitive-data patterns automatically flagged (credit card numbers, SSNs, emails, phone numbers, dates of birth — mapped to PCI-DSS/PII/GDPR tags)

### 6. Security Policy Configuration

Create a base policy (`Oracle_19c_Production_Security_Policy`) applied to the service/group above, assigned to all relevant gateways, priority **High (100)**, status **Enabled**. Configure the following rules under it:

| # | Rule | Key configuration | Actions | Severity |
| --- | --- | --- | --- | --- |
| 1 | Monitor Privileged DBA Activity | Users: `SYS`, `SYSTEM`, `DBA_ADMIN`; all operations (SELECT/INSERT/UPDATE/DELETE/DDL/DCL) | Audit + Alert | High |
| 2 | Detect SQL Injection Attempts | Signatures + pattern matching + ML: UNION-based, boolean-based (`OR 1=1`), time-based (`WAITFOR DELAY`, `DBMS_LOCK.SLEEP`), comment injection, stacked queries | Audit + Alert + Block (session termination) | Critical |
| 3 | Monitor Sensitive Data Access (PII/PCI) | Tables: `CUSTOMERS`, `CREDIT_CARDS`, `EMPLOYEES`; tags PCI-DSS/PII/GDPR; bulk threshold > 1000 rows | Audit + Alert | Medium (High for bulk access) |
| 4 | Detect After-Hours Database Access | Mon–Fri 18:00–06:00, Sat–Sun all day; excludes `BATCH_USER`, `MONITORING_USER`, `BACKUP_USER` | Audit + Alert (email + SMS to on-call) | High |
| 5 | Monitor Failed Login Attempts | 5 failures in 10 minutes per IP/username; ML-based brute-force detection | Audit + Alert + Block IP (1 hour) | High |
| 6 | Detect Data Exfiltration | Rows > 10,000 or data volume > 100 MB; `SELECT ... OUTFILE`/`SPOOL`/bulk export; full table scans; excludes reporting/ETL/BI accounts | Audit + Alert (CISO escalation if > 100,000 rows) | Critical |
| 7 | Monitor Database Configuration Changes | `ALTER SYSTEM`/`ALTER DATABASE`/`CREATE`/`DROP USER`, `GRANT`/`REVOKE`; scoped to approved maintenance window | Audit + Alert + change-request validation | High |
| 8 | Detect Excessive Privilege Usage | Privileged roles (`sysadmin`/`db_owner`-equivalent DBA roles) performing routine SELECT/UPDATE work | Audit + Alert + weekly usage report | Medium |

**Alert action configuration**

- **Email:** template subject `[IMPERVA ALERT] ${SEVERITY} - ${RULE_NAME}`, body includes `${TIMESTAMP}`, `${SEVERITY}`, `${RULE_NAME}`, `${DATABASE_NAME}`, `${DB_USER}`, `${SOURCE_IP}`, `${SQL_TEXT}`, and `${ALERT_URL}`.
- **SIEM (Syslog/CEF):** forward to `<siem_ip>:514`, TCP, format CEF, facility `Local4`; severity mapping Critical→Emergency(0), High→Alert(1), Medium→Warning(4), Low→Notice(5).
- **ServiceNow incident creation:** webhook (REST, POST, Basic Auth) to the incident table; trigger only on Critical/High severity, throttled to a maximum of 10 incidents/hour; payload includes alert description, DB/user context, SQL statement, and severity.

### 7. Testing and Validation

**Agent connectivity**
```bash
systemctl status ragent
tail -100 /opt/imperva/ragent/logs/ragent.log | grep -E "ERROR|WARN|Connected"
curl -k https://<gateway_primary_ip>:443
top -p $(pgrep ragent)
netstat -an | grep 443 | grep ESTABLISHED
```
In the MX Console, confirm the agent shows **Connected (green)**, heartbeat < 30 seconds, CPU < 10%, memory ~1.5 GB, and the monitored database (`orcl`) as **Active**.

**Database traffic capture validation**
```sql
-- From SQL*Plus or SQL Developer
SELECT * FROM CUSTOMERS WHERE customer_id = 1;
SELECT COUNT(*) FROM ORDERS;
UPDATE CUSTOMERS SET email = 'test@example.com' WHERE customer_id = 999;
DELETE FROM temp_table WHERE created_date < SYSDATE - 30;
EXEC process_order(1234);
CREATE TABLE test_table (id NUMBER);   -- should trigger a DDL alert if monitored
```
Verify in **Monitoring → Live Monitoring → Database Activity** (filter to the service, last hour) that every statement appears with full SQL text, user identity, source IP, execution time, rows affected, and success/failure status.

**Security policy rule testing**
| Test | Sample statement(s) | Expected result |
| --- | --- | --- |
| SQL injection | `... WHERE username = 'admin' OR '1'='1'`; `UNION SELECT username, password FROM users` | `Detect_SQL_Injection_Attempts` fires, Critical, email to security/SOC, SIEM event, session blocked if blocking enabled |
| Privileged user monitoring | `ALTER SYSTEM SET processes=300 SCOPE=SPFILE;` `GRANT DBA TO testuser;` `DROP TABLE test_table;` (as SYSTEM) | `Monitor_Privileged_DBA_Activity` fires, High, email to DBA team, full audit entry |
| Sensitive data access | `SELECT * FROM FINANCIAL.CREDIT_CARDS;` `SELECT card_number, cvv FROM FINANCIAL.CREDIT_CARDS WHERE customer_id = 123;` | `Monitor_PII_PCI_Data_Access` fires, Medium, PCI-DSS tag, email to compliance |
| Failed logins | 6 consecutive failed `sqlplus` connections | `Monitor_Failed_Login_Attempts` fires after the 5th failure within 10 minutes, High, source IP blocked 1 hour, ServiceNow ticket created |

**Performance impact testing**
| Metric | Baseline (pre-Imperva) | With Imperva | Acceptable threshold |
| --- | --- | --- | --- |
| SQL response time | 10 ms avg | 10.3 ms avg | < 5% increase |
| Agent CPU usage | N/A | 7% | < 10% |
| Agent memory | N/A | 1.8 GB | < 2 GB |
| Database CPU | 45% | 48% | < 10% increase |
| Network overhead | N/A | 3 Mbps | < 5 Mbps |

**Audit log validation**

In **Monitoring → Audit → Database Audit**, filter to the service and the test window, confirm every activity is logged with full SQL text, bind variables, user identity, source IP, execution time, policy matches, and alert status, then export the audit report for the deployment record.

### 8. Production Rollout and Hardening

**Re-enable SELinux with a generated policy**
```bash
cd /opt/imperva/ragent/selinux
grep ragent /var/log/audit/audit.log | audit2allow -M imperva_ragent
semodule -i imperva_ragent.pp

setenforce 1
vi /etc/selinux/config
# SELINUX=enforcing

getenforce
systemctl restart ragent
systemctl status ragent
```

**Replace the self-signed agent certificate with a CA-signed one**
```bash
cd /opt/imperva/ragent/certs
openssl req -new -newkey rsa:2048 -nodes \
  -keyout agent.key -out agent.csr \
  -subj "/C=US/ST=CA/O=Company/CN=ora-db01.company.local"

# Submit agent.csr to your CA, then install the signed certificate:
cp agent.crt /opt/imperva/ragent/certs/
cp agent.key /opt/imperva/ragent/certs/
chmod 600 /opt/imperva/ragent/certs/agent.key
chown imperva:imperva /opt/imperva/ragent/certs/*

vi /opt/imperva/ragent/config/agent.conf
# verify_gateway_cert = true

systemctl restart ragent
```

**High availability — auto-restart**
```bash
vi /usr/lib/systemd/system/ragent.service

[Service]
Type=forking
User=imperva
ExecStart=/opt/imperva/ragent/bin/ragent start
ExecStop=/opt/imperva/ragent/bin/ragent stop
Restart=always
RestartSec=10
StartLimitInterval=300
StartLimitBurst=5

systemctl daemon-reload
systemctl enable ragent
```

**Automated health-check script** (schedule via `cron`, e.g. every 5 minutes):
```bash
#!/bin/bash
# Imperva Agent Health Check
AGENT_LOG="/opt/imperva/ragent/logs/ragent.log"
EMAIL="dba-team@company.com"

if ! systemctl is-active --quiet ragent; then
  echo "CRITICAL: Agent not running" | mail -s "Agent Down" $EMAIL
  systemctl start ragent
fi

ERROR_COUNT=$(grep -c "ERROR" <(tail -1000 $AGENT_LOG) || echo 0)
if [ $ERROR_COUNT -gt 10 ]; then
  echo "WARNING: $ERROR_COUNT errors detected" | mail -s "High Errors" $EMAIL
fi
# */5 * * * * /usr/local/bin/monitor_imperva_agent.sh
```

### Appendix — Finding the Correct Agent Package for Non-Windows Hosts (`which_ragent.sh`)

Because there is only one Windows agent build but many Linux/Unix kernel variants, use the `which_ragent.sh` reconnaissance script whenever installing on anything other than Windows:

1. On the Imperva FTP site, go to **Downloads → Securesphere Agents → Miscellaneous** and download the `which_ragent` tarball (gzip) and, if your kernel requires it, the companion **KABI** file.
2. Unpack it:
   ```bash
   mkdir witch_agent && cd witch_agent
   tar -xzvf which_ragent-<version>.tar.gz
   ```
3. Run the script, specifying the target agent version (e.g. `14.0000` for a 14.9 agent):
   ```bash
   ./which_ragent.sh -v 14.0000
   ```
4. The script reports the detected OS, OS version, platform, and kernel, then names the exact agent package to look for.
5. Go back to the Imperva FTP site under **Downloads → Imperva Agents → <version> → <OS>**, and locate the matching package (if the exact filename isn't present, check one version back). Download it and proceed with **Phase 0, Step 2** above.
